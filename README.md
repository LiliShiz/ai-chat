# Чат с языковой моделью

Одностраничный веб-чат поверх OpenRouter: потоковый ответ, обрыв генерации
на середине, внятные состояния на каждой аварии. Ключ живёт на сервере и в
браузер не попадает.

React 19 + TypeScript + Vite · Node + Hono · SSE

[![CI](https://github.com/LiliShiz/ai-chat/actions/workflows/ci.yml/badge.svg)](https://github.com/LiliShiz/ai-chat/actions/workflows/ci.yml)

![Пустое состояние](docs/empty-state.png)

## Запуск за пять минут

```bash
git clone <этот-репозиторий>
cd ai-chat
npm install

cp .env.example .env        # Windows: copy .env.example .env
# впишите в .env ключ с https://openrouter.ai/keys

npm run dev
```

Открыть **http://localhost:5173**. Всё.

Нужен Node ≥ 20.12 — `.env` грузится через `process.loadEnvFile`, который
появился именно в этой версии. Проверялось на Node 22 (CI) и 23.

> **Если модель ответила «This model is unavailable for free»** — значит
> она уехала из бесплатного каталога (так уже случилось по ходу работы, и
> не один раз). Возьмите любую живую:
> ```bash
> curl -s https://openrouter.ai/api/v1/models \
>   | jq -r '.data[] | select(.id | endswith(":free")) | .id'
> ```
> и впишите в `OPENROUTER_MODEL`. Правка кода не нужна.

### Посмотреть, как выглядят аварии, — без ключа

В репозитории есть поддельный OpenRouter. Он нужен, потому что 429, таймаут
и обрыв связи на живом апстриме ловятся «когда повезёт», а проверять
обработку ошибок по случайному совпадению — значит не проверять её вовсе.

```bash
npm run dev:mock
```

Дальше просто пишите в чат сообщение с маркером:

| Маркер | Что произойдёт |
|--------|----------------|
| *(без маркера)* | Обычный ответ с markdown, списком и блоком кода |
| `#long` | Длинный ответ — удобно жать «Стоп» |
| `#429` | Лимит бесплатной модели + `Retry-After` и обратный отсчёт |
| `#timeout` | Соединение открыто, ответа нет — сработает сторожевой таймер |
| `#stall` | Стрим начался и замолчал — сработает idle-таймер |
| `#cut` | Жёсткий обрыв посреди стрима |
| `#error` | Ошибка приходит событием внутри уже открытого потока |

## Что я сделал иначе, чем написано в ТЗ

### Обводка фокуса

> «Уберите стандартную браузерную обводку фокуса (`outline`) у кнопок и поля
> ввода — в разных браузерах она выглядит разнобойно и портит аккуратный вид.»

Это требование противоречит другому требованию того же ТЗ:

> «Доступность: интерфейсом можно полноценно пользоваться с клавиатуры —
> Tab по элементам…»

Убрать `outline` и ничего не дать взамен — значит сделать клавиатурную
навигацию непригодной: человек жмёт Tab и не понимает, где находится.
Это прямое нарушение WCAG 2.4.7 Focus Visible (уровень AA) и, в отличие
от «разнобойного вида», ломает не эстетику, а работоспособность.

**Что сделано.** Дефолтная обводка снята — та самая, которая выглядит
по-разному в Chrome, Safari и Firefox. Вместо неё свой `:focus-visible`:
аккуратное кольцо в цвет интерфейса, одинаковое во всех браузерах.
Ключевое — именно `:focus-visible`, а не `:focus`: кольцо появляется при
навигации с клавиатуры и не появляется при клике мышью.

![Кольцо фокуса на кнопке](docs/focus-ring.png)

Требование выполнено по существу (разнобойной обводки нет, вид аккуратный),
а доступность не сломана.

Отдельно стоит сказать, что именно этот приём и оказался самым хрупким
местом работы. Он трижды ломался незаметно:

- в режиме высокой контрастности Windows браузер отбрасывает `box-shadow` —
  добавлен блок `@media (forced-colors: active)` с настоящим `outline`;
- у кнопки «К последнему» собственная тень перебивала общее правило по
  порядку в файле — кольцо вынесено в переменную `--focus-ring`, чтобы
  элементы со своей тенью дорисовывали его рядом;
- у переключателя темы кольцо срезал `overflow: hidden` родителя, а у
  действий внутри ленты — сама прокручиваемая лента.

Тест на это тоже переписывался дважды: сначала он проверял «тень не `none`»
и проходил при удалённом кольце, потом читал `getComputedStyle` и не видел
обрезку предком. Сейчас он обходит интерфейс табом, поднимается по предкам
и проверяет, что вокруг кнопки остаётся место под кольцо.

### Ещё две мелочи на ту же тему

- **Поле ввода — `textarea`, а не `input`.** ТЗ говорит «поле ввода», но
  Shift+Enter для переноса строки в `input` не сделать, а без него чат
  неудобен для любого текста длиннее фразы.
- **`role="alert"` на блоке ошибки.** В ТЗ этого нет, но требование
  «пользователь видит понятное состояние» для незрячего выполняется только
  так: иначе про ошибку он узнает, лишь добравшись до неё табом.

## Ключевые решения

### Где живёт ключ

Браузер знает ровно два адреса: `/api/health` и `/api/chat`. Ключ читается
из окружения в `server/src/config.ts` и не покидает процесс — его нет ни
в бандле, ни в одном запросе со страницы.

В dev это не иллюзия из-за CORS: Vite проксирует `/api` на сервер, так что
во вкладке Network видно ровно то же, что будет в проде — свой origin и ни
одного обращения к `openrouter.ai`.

```
браузер ──POST /api/chat──▶ Vite (dev) ──▶ Hono :8787 ──▶ openrouter.ai
        ◀────── SSE ───────                             (здесь и только
                                                         здесь есть ключ)
```

### Ошибка — это событие в потоке, а не HTTP-статус

Прокси не пробрасывает формат OpenAI как есть. Я разбираю SSE на сервере и
отдаю свой, узкий протокол из трёх событий:

```ts
{ type: 'delta',  text: string }
{ type: 'done',   reason: 'stop' | 'length' | 'unknown' }
{ type: 'error',  error: { code, message, retryable, retryAfterSec? } }
```

Первая причина — фронт не должен знать, какой провайдер стоит за прокси.
Вторая важнее. Ответ 429 до начала генерации ещё можно отдать статусом. Но
лимит может прилететь **после** двадцати уже полученных токенов, а сеть —
оборваться на середине. Статус к тому моменту уже отправлен (`200 OK`),
менять его поздно.

Поэтому ошибка приезжает отдельным событием поверх уже открытого потока.
Клиент дорисовывал текст по мере поступления — значит, полученный кусок
никуда не девается, и рядом с ним появляется объяснение, что случилось.
Ровно это требует ТЗ от кнопки «Стоп», и ровно это правильно для аварий.

### Отмена доходит до апстрима

`AbortController` прошит насквозь: кнопка «Стоп» → `fetch` на клиенте →
`c.req.raw.signal` в Hono → `fetch` к OpenRouter. Не «спрятать текст в UI»,
а действительно прекратить генерацию: иначе модель продолжает считать
токены в пустоту и жечь и без того скромную бесплатную квоту.

### Два таймаута вместо одного

Один общий таймаут на запрос — плохая идея: длинный честный ответ и
зависшее соединение выглядят для него одинаково. Здесь их два: ожидание
первого токена (45 с, бесплатные модели часто стоят в очереди) и пауза
между токенами (30 с, сторож перезаводится на каждом чанке). Пока модель
печатает, соединение считается живым сколько угодно долго.

### История: `sessionStorage`

ТЗ отдаёт это решение кандидату. Мой выбор и почему:

- **«Не хранить вовсе»** отпадает сразу: случайный F5 или свайп «назад» на
  телефоне стирает весь диалог. Это не фича, это потеря данных.
- **`localStorage`** живёт вечно и глобально для origin. В переписку с LLM
  люди вставляют рабочий код, письма, персональные данные. Оставлять их на
  машине до ручной очистки — плохой дефолт, особенно если машина общая.
- **`sessionStorage`** даёт ровно то, что просит формулировка «в рамках
  сессии»: переживает перезагрузку, умирает вместе с вкладкой, не течёт в
  соседние вкладки.

Долгая история — это уже не storage, а аккаунт и сервер, с явным
управлением и кнопкой «удалить». Это другая задача.

### Оформление: почему антиква, а не пузыри

Ответ языковой модели — это текст, который читают: абзацы, списки, блоки
кода, иногда на три экрана. Пузырь сообщает «прими сообщение», а не
«прочитай материал», поэтому ответ модели набран как статья: антиква
(Literata), кегль 17px, интерлиньяж 1.68, мера 66 знаков, без карточки и
рамки. Плашка осталась только у реплики человека — её не читают, её
опознают. Всё служебное (шапка, метки, рубрики, кнопки) моноширинное:
иерархию держит шрифт, а не рамки и заливки. Акцентный цвет один.

Перед этим я собрал четыре черновых направления и сравнил их на одном и том
же диалоге — макеты лежат в `.planning/sketches/`, открываются как обычные
HTML-файлы.

Тема — **светлая, тёмная и системная**, а не тумблер на два положения:
тумблер навсегда отвязывает интерфейс от настройки ОС. Реализовано одним
свойством: все токены объявлены через `light-dark()`, который читает
`color-scheme`, так что смена темы — это смена `color-scheme` на `<html>`.
Бонусом перекрашиваются скроллбары и системные элементы формы.

Шрифты подключены локально (`@fontsource`), а не с Google Fonts: нет
запроса к третьей стороне и нет утечки IP пользователя в чужую аналитику.

### Мелочи, которые заметны только в работе

- Токены копятся в буфере и выливаются в state раз в кадр. Без этого каждый
  токен перерисовывает всю ленту.
- При остановке дописывается хвост буфера — иначе терялись бы последние
  символы ровно в момент нажатия «Стоп».
- Автопрокрутка работает, только если пользователь и так внизу. Иначе
  нельзя перечитать начало длинного ответа.
- Пустой ответ при ошибке убирается из ленты, а вопрос остаётся —
  «Повторить» отправляет именно его.
- Подсветка кода ждёт конца потока: разбор на каждом токене — это O(n²) по
  длине листинга, а толку от подсветки обрывка нет.
- Markdown с подсветкой вынесен в ленивый чанк и прогревается в простое;
  подсветка собрана на шести языках вместо сорока (337 → 213 КБ).

## Тесты

```bash
npm test      # 69 юнит-тестов
npm run e2e   # 21 сценарий в браузере
```

Покрыто не «рендерится без падения», а то, что ломается.

**Сервер.** Разбор SSE: кадр, разорванный между сетевыми чанками;
keep-alive комментарии апстрима; битый JSON. Маппинг ошибок: 429 с
`Retry-After`, 401 без утечки наружу того, что дело в ключе, 5xx как
временная. Отдельно — главное свойство протокола: ошибка посреди потока
приходит **после** уже отданного текста. Отмена: «Стоп» завершает поток
молча и рвёт соединение с апстримом. Оба сторожевых таймера проверяются
фальшивыми таймерами, без реального ожидания. Плюс валидация запроса,
лимит тела (в том числе обход через chunked) и проверка, что ключ уходит
ровно в одном месте.

**Фронт.** Чтение потока, отмена как отдельный исход, offline без запроса
в сеть. История: `sessionStorage`, мусор в хранилище, записи чужого
формата, недоступная квота. Машина состояний: остановка сохраняет кусок,
пустой пузырь не остаётся, повтор отрезает неудачный ответ. Отдельно —
работа без `crypto.randomUUID` и `navigator.clipboard`, которых нет вне
защищённого контекста.

**E2E** гоняются против поддельного апстрима в настоящем браузере.
Стриминг проверяется как стриминг: длина текста снимается дважды, вторая
обязана быть больше. Дальше — Esc и «Стоп», 429 с живым отсчётом, обрыв
посреди потока, молчащий апстрим, настоящий offline через
`context.setOffline`, отсутствие обращений наружу, история и тема через F5,
вся клавиатура, кольцо фокуса на каждой кнопке, семантика, 375×720 и
390×600 без переполнения, тач-таргеты от 44px.

### Мутационная проверка

Набор, который проходит при сломанном коде, хуже, чем его отсутствие:

| Что ломал | Что упало |
|---|---|
| Флаг «остановлено» в `useChat` | Тест про сохранение прерванного ответа |
| Обе проверки `aborted` в `openrouter.ts` | Два теста про отмену |
| Сверка контроллера на идентичность | Тест про «Стоп → сразу отправить» |
| Отсев пустых реплик при сборке истории | Тест про «Стоп до первого токена» |
| Ретрансляция отмены на апстрим | Два теста про «Стоп» |
| `overflow: hidden` у переключателя темы | E2E про кольцо фокуса |

Первые версии некоторых тестов эту проверку не прошли бы — разбор в
[ИИ-логе](docs/AI-LOG.md).

### CI

`.github/workflows/ci.yml` — две задачи. Первая: линт, типы, тесты, сборка
и дымовой прогон прод-режима. Последний поднимает `npm start` поверх
поддельного апстрима и проверяет, что по `/` приходит **собранный** фронт
(ищется хешированный ассет, а не строка, которая есть и в исходном
`index.html`), что в бандле нет ключа, что `/api/chat` действительно
стримит и что неизвестный `/api`-путь отдаёт JSON-404. Вторая задача —
E2E с отчётом-артефактом при падении.

## Что не вошло и что сделал бы за ещё день

- **Ретрай с экспоненциальной задержкой** на 429 и 5xx — сейчас повтор
  ручной, кнопкой. Бесплатные модели отваливаются часто, автоматический
  бэкофф с уважением к `Retry-After` был бы уместнее.
- **Выбор модели из UI.** Каталог `:free` меняется, и захардкоженная модель
  однажды исчезает — это уже случалось дважды за два дня. Правильнее тянуть
  `/api/v1/models`, фильтровать и давать выбрать.
- **Виртуализация ленты.** На тысяче сообщений DOM начнёт тормозить.
- **Продолжение прерванного ответа.** Сейчас у остановленного есть пометка,
  но продолжить с того же места нельзя — только перегенерировать целиком.
- **Реальное устройство под iOS.** Android проверен вживую (и это нашло
  дефект, который не показала ни одна эмуляция), iPhone под рукой не было.

## Как я это делал

Процесс вёлся по GSD: `.planning/` лежит в репозитории — контекст проекта,
требования с ID, дорожная карта и журнал решений. Требования привязаны к
фазам, фазы — к веткам и PR. Коммиты атомарные, история читается сверху
вниз как рассказ о том, что происходило.

### Сколько это заняло

ТЗ просило 2–6 часов чистого времени. По истории коммитов вышло **около 5
часов** за девять подходов: коммиты сгруппированы в сессии с разрывом
больше 45 минут, к каждой добавлено по 12 минут на работу до первого
коммита. Календарно между первым и последним коммитом — 29 часов,
остальное паузы.

| | |
|---|---|
| Кода (TS/TSX/CSS/HTML) | ~6 100 строк |
| Из них тесты | ~1 900 строк |
| Коммитов / слитых PR | 30 / 16 |
| Тестов | 69 юнит + 21 браузерный |

Примерно половина этого времени ушла не на то, чтобы написать работающий
чат — он был готов к концу первого подхода, — а на то, чтобы убедиться,
что он действительно работает.

### ИИ-лог

Писал с **Claude Code** (модель Opus). Архитектуру, протокол между фронтом
и прокси и все решения выше формулировал сам; ИИ писал код, я ревьюил
каждую строку и правил.

Полный разбор — **[docs/AI-LOG.md](docs/AI-LOG.md)**: 31 пункт с
конкретикой, где именно ИИ ошибся, как это было замечено и чем чинилось.
Там же — находки четырёх заходов внешнего ревью и проверка на живом
телефоне.

Три самых дорогих:

1. **Приложение не работало ни на одном телефоне.** `crypto.randomUUID()`
   существует только в защищённом контексте; страница по http на IP этого
   метода не видит, и отправка падала `TypeError` прямо в обработчике — без
   запроса, без ошибки на экране. Ни один из 90 тестов этого не поймал,
   потому что все они ходят на `localhost`, а он всегда защищённый.
2. **Вакуумные тесты дважды.** Тест на отмену проходил при полностью
   удалённой логике отмены: безусловный `finally { upstream.abort() }`
   делал ассерт истинным всегда. Тест на кольцо фокуса проходил при
   удалённом кольце, потому что `includes('4px')` срабатывал на `14px` из
   декоративной тени.
3. **Документация опережала код.** `npm start`, который «отдаёт фронт», но
   не выставлял `NODE_ENV`; коммит с названием «фикс» без фикса; `engines`
   со ссылкой на флаг, от которого давно отказались. Ни одно из этих
   расхождений не было враньём в момент написания — все возникли молча.

Общий вывод: ИИ хорошо пишет то, что уже решено, и уверенно ошибается там,
где надо было проверить — в разметке, в краевых значениях и в фактах о
внешнем мире. И отдельно: **localhost — не репрезентативная среда**. Он
даёт защищённый контекст, отсутствие сети между фронтом и бэкендом и
идеальную задержку. Трёх вещей, которых в реальности нет.

```
.
├── server/                  Прокси: ключ, ретрансляция SSE, ошибки
│   └── src/
│       ├── index.ts             точка входа: поднимает порт
│       ├── app.ts               маршруты, ReadableStream ответа
│       ├── openrouter.ts        запрос к апстриму, таймауты, разбор SSE
│       ├── protocol.ts          контракт с браузером
│       ├── config.ts            окружение
│       └── dev/mock-upstream.ts поддельный OpenRouter
├── web/
│   └── src/
│       ├── App.tsx              каркас, Esc, статус
│       ├── hooks/
│       │   ├── useChat.ts       состояние диалога, отмена, повтор
│       │   ├── useTheme.ts      светлая / тёмная / системная
│       │   └── useCopy.ts       копирование с отметкой
│       ├── lib/
│       │   ├── streamChat.ts    чтение SSE на клиенте
│       │   ├── history.ts       sessionStorage
│       │   ├── highlight.ts     подсветка на шести языках
│       │   └── id.ts            UUID без защищённого контекста
│       ├── components/
│       │   ├── Composer.tsx     ввод, авторесайз, горячие клавиши
│       │   ├── MessageList.tsx  лента, действия, «К последнему»
│       │   ├── Markdown.tsx     ленивый чанк: markdown + подсветка
│       │   ├── ThemeToggle.tsx  переключатель темы (радиогруппа)

│       └── styles.css           токены, темы, фокус, подсветка
├── e2e/                     браузерные сценарии (Playwright)
│   ├── chat.spec.ts             диалог, отмена, аварии, история, тема
```
